# A Constraint-Fulfilling, Cell-Aware Analog Place-and-Route Feedback Loop with Free Signoff Oracles — Algorithm, Mathematics, and a GPU Work-Span Analysis

## TL;DR

- **Build the loop as a two-level augmented-Lagrangian / feasibility-pump engine that treats the free DRC/PEX/LVS oracles as _gradient-like signals sampled every move_, not as terminal gates.** Hard exact constraints (symmetry axes, integer ratios, LVS structure, trench disjunctions) belong in the _representation and the projection operator_ so they are satisfied by construction; budget-type constraints (coupling sums, thermal gradients, parasitic budgets) belong in an adaptive penalty/multiplier layer; PEX minimization is the _innermost objective, lexicographically dominated_ by feasibility. Certainty of zero-DRC comes from making the search move in a legal-by-construction subspace and using the oracle only to detect the residual placement-induced (implant-merge) violations that construction cannot foresee.
- **Variant selection must be a first-class search variable solved jointly with placement, because a variant change discontinuously relocates pins and therefore discontinuously changes routability and extracted parasitics.** The right mechanism is a _price-directed, group-coupled discrete search_: enumerate the (constrained) per-group variant product space, price each hypothesis with a batched oracle evaluation, and let variant swaps be moves inside the same annealing/relaxation loop as placement — with same-variant and integer-ratio requirements collapsing the group product space to a small number of legal joint assignments.
- **On GPU: the placer itself is "thin" at analog device counts (tens–thousands), but the free oracles make the engine "wide" in a different dimension.** The real GPU leverage is (i) massively **batched candidate/replica evaluation** (thousands of hypothetical moves/variants/layouts scored in parallel by GPU DRC/PEX/thermal kernels), (ii) **parallel-tempering** replica-exchange search, and (iii) the **FFT/stencil field solves** (electrostatic density _and_ the placement-dependent thermal PDE) that are natively GPU-friendly. Single-trajectory DREAMPlace-style speedups do **not** transfer; GPU detailed routing does not transfer; GPU global routing (InstantGR/GAMER/FastGR) and GPU DRC (X-Check/OpenDRC) partially transfer.

---

## Key Findings

1. **No published system solves the stated problem.** ALIGN, MAGICAL, BAG/BAG2, and the commercial tools (Cadence Virtuoso, Synopsis Custom Compiler, Pulsic Animate) each handle _subsets_ — symmetry, common-centroid, generator-based devices, concurrent P&R — but none is architected around free, arbitrarily-callable DRC/PEX/LVS oracles used as an inner-loop signal. The free-oracle regime is genuinely novel and changes the optimal architecture: it converts verification from a cost to be amortized into a _dense feedback field_ that can be sampled per move.

2. **The constraint set is heterogeneous and cannot be handled by one mechanism.** It contains (a) exact integer equalities, (b) disjunctive/non-convex feasible sets, (c) set-level accumulating budgets, (d) constraints on placement-derived state (thermal field), and (e) constraints whose existence depends on the placement (guard-ring sharing, injector exclusion). Each class has a _distinct_ correct algorithmic treatment; a single scalarized penalty objective provably fails classes (a), (c), and (e).

3. **Topological placement representations (sequence-pair, B\*-tree, TCG) already give exact symmetry/common-centroid by construction** — this is the correct home for the hard equalities, and it is well-established (Balasa–Lampaert symmetric-feasible sequence pairs; ASF-B*-tree; TCG-S). Analytical placers (ePlace/RePlAce/DREAMPlace, and MAGICAL's analytical placer) give smooth gradients but only *approach\* equalities asymptotically — which is exactly the failure mode the brief names.

4. **GPU EDA wins are workload-size-dependent.** DREAMPlace reports "over 30× speedup in global placement and legalization… a design with one million cells finishes in one minute" over multi-threaded CPU (RePlAce) on ISPD 2005 benchmarks with an NVIDIA Tesla V100 (Lin et al., DAC 2019; the journal version cites around 40×). Its integrated GPU detailed placer ABCDPlace (Lin, Li, Gu, Ren, Khailany, Pan, IEEE TCAD 2020) delivers over 16× speedup on industrial benchmarks over CPU implementations. Both come from million-cell designs. Analog blocks have tens–thousands of devices. The parallel _slack_ for a single placement trajectory is therefore small, and kernel-launch/PCIe overheads dominate — a "thin" verdict for the placer proper. The leverage migrates to batch/population/field dimensions.

## Details

### 1. Loop Architecture

**Recommended structure: a three-tier nested loop with an outer discrete search over variant/topology, a middle constraint-satisfaction (feasibility) solver, and an inner continuous parasitic-minimization refinement — all sharing one free-oracle evaluation service.**

```
OUTER  (discrete): variant assignment V, topology/representation T, symmetry-axis
                   and centroid-group structure, guard-ring grouping hypothesis
  MIDDLE (feasibility): augmented-Lagrangian / feasibility-pump over positions x on
                        the integer grid, projecting onto exact-equality manifold,
                        driving all budget constraints to satisfaction
    INNER (optimization): minimize PEX (R, C, coupling) subject to the active
                          constraint set, via legal local moves / continuous relaxation
    ORACLE SERVICE: drc(), pex(), lvs() callable at every granularity
```

**Why this decomposition (and why the alternatives lose):**

- _Fully joint (one giant MINLP over variant, position, route simultaneously)_ is the theoretically "correct" formulation but is intractable and — more importantly — wastes the free oracle. It gives no natural place to inject per-move signoff feedback. **Loses on tractability and on not exploiting the central degree of freedom.**
- _Fully sequential (choose variants → place → route, each frozen)_ is the classic digital pipeline and the historical analog-tool failure mode. The patent literature describing the motivation for concurrent analog tools frames it directly: "For an optimal analog layout, placement must be performed in the context of routing, and likewise routing is dependent on placement… An analog designer would consider both simultaneously." Pulsic markets Animate on exactly this claim — "truly simultaneous placement and routing" via its PolyMorphic technology. Freezing footprints before placement is impossible here because footprint is an output. **Loses because the couplings the brief describes are real and discontinuous.**
- _The recommended nesting_ is justified by a **separation-of-timescales argument**: variant/topology choices are discrete and low-cardinality (after constraint collapse — see §2), so they belong in an outer search that changes rarely; position feasibility is a medium-frequency continuous/integer problem; parasitic polishing is high-frequency and local. Decisions that are genuinely coupled (variant↔pin-position↔routability) are kept in the _same_ outer+middle scope and co-evaluated by the oracle; decisions that are only weakly coupled (final wire-width tapering to hit a resistance budget) are nested innermost without loss.

**Where the oracle calls belong, and at what granularity:**

- **DRC:** call _incrementally per accepted move_ on the local bounding box of the change (the oracle is free, so we can also call it per _candidate_ move in a batch — see GPU §8). Its role is not "final check" but _repair signal_: which rule, which layer, which geometry. Because most moves are legal-by-construction (§3a), DRC's real job is catching the residual placement-induced violations (abutment/implant merges) that construction cannot predict.
- **PEX:** call _per epoch_ for the objective value, and _per candidate move_ for the innermost parasitic-minimization gradient estimate (finite-difference over the free oracle). Coupling capacitance must be recomputed on the _set_ of neighbours (§4c), so PEX is queried on a spatial neighbourhood, not pairwise.
- **LVS:** call _per epoch and whenever a variant/topology move changes device structure_. LVS is the guard against extraction-ambiguity created by placement (§3c); it must run after any move that can merge diffusions or change device identity.

**State carried between iterations:** the variant assignment V, the topological representation T (sequence-pair/B\*-tree encoding the exact symmetry and centroid structure), the multiplier vector λ and penalty weights ρ (augmented-Lagrangian state), the history-cost field for routing negotiation (PathFinder-style, see §4e), and the best feasible incumbent. **Recomputed each iteration:** the thermal field (placement-dependent PDE), the parasitic values (PEX), the guard-ring geometry (depends on current placement), and the DRC violation set.

### 2. Cell-Awareness: coupling variant choice to placement and routing

**Mechanism: price-directed, group-coupled discrete variant search embedded in the outer loop, with pin-movement treated as a discontinuity that forces re-evaluation rather than interpolation.**

Because changing a variant moves pins, the extracted parasitics and routability are **discontinuous in the variant index** — there is no gradient to follow across variants. This rules out any relaxation that treats the variant as continuous. The correct formalism is a **discrete optimization with an oracle-priced objective**:

For matched group g with target integer ratio r_g and the same-variant flag, the _joint_ variant of the group is not a free product of per-device choices. The same-variant-required and exact-integer-ratio requirements act as **equality constraints on the group's variant vector**, collapsing the naive product space |Var|^{|g|} to the small set of assignments that (i) use one variant family, (ii) decompose the ratio into identical unit fingers/segments (FETs parallel, R/C series), and (iii) admit a legal interleaving pattern (Single/ABAB/ABBA/checkerboard) for that family. This is exactly the ALIGN/MAGICAL "primitive generator + array" structure, but here the _choice among_ array aspect ratios and metal-stack constructions is a search variable, not a fixed recipe. (Note the BJT rule the brief states: area ratios come from unit-device count, never emitter scaling — a 1:8 bandgap is eight unit devices — which is a hard structural constraint on the collapse, not a preference.)

**Search/pricing procedure:**

1. **Enumerate** the collapsed legal joint-variant set per group (small: typically a handful to low hundreds after constraint collapse).
2. **Price** each hypothesis by _actually drawing it_ (generators are deterministic — byte-identical geometry) and calling the free oracle on a representative placement/route stub: footprint, pin map, internal parasitics, matching quality, and — crucially — a _routability/parasitic estimate_ from a fast batched route of the group's nets. This is where the free oracle earns its keep: instead of a learned surrogate (ALIGN's ML constraint evaluators of Dhar et al.), we can _measure_ the consequence.
3. **Select or keep-as-move:** either fix the priced-best variant up front (cheap, but myopic because it ignores where the device lands), or — recommended — keep variant swaps as _moves_ in the outer search so the assignment can be revised when placement feedback shows the priced choice is dominated. The recommended answer is **hybrid**: price up front to seed, then allow variant moves conditioned on oracle feedback.

**Why alternatives lose:** Up-front pricing alone (BAG-style generate-then-evaluate) is myopic — it cannot know pin-position consequences before placement. Pure "variant as annealing move" without pricing wastes moves on obviously dominated variants. A continuous relaxation of the variant index is _invalid_ because the objective is discontinuous there. The group-coupling insight (variants of different devices in one matched group are not independently choosable) is what makes the search tractable: it is the constraint that shrinks the space. Note the capacitor case sharpens the discontinuity: the three metal-stack constructions (single-layer comb, two-metal parallel-plate, three-metal sandwich) are _topologically_ different devices with different pin faces and a load-bearing inter-plate dielectric — a via cut inside a stacked-plate footprint shorts the device — so a variant move here changes not only pins but the LVS-legality of the surrounding routing.

### 3. Attaining the Three Targets

**(a) Certain zero DRC, not "zero on this seed."**

Certainty requires that the search move in a **legal-by-construction subspace** for everything construction can guarantee, and use the oracle to _close_ the residual. Concretely:

- Draw every device with a deterministic, individually-DRC-clean generator (given). Place on a **design-rule-correct grid** (ALIGN's simplified-grid abstraction, which "attempts to abstract the design rules using a simplified grid") so inter-device spacing violations are structurally impossible for the common rules.
- The residual class DRC construction cannot foresee is **placement-induced merges**: two abutting DRC-legal devices whose implant/well layers merge. This is caught by the oracle and repaired by a spacing/keepout move.
- **Repair-oscillation failure mode** (fixing rule A re-creates rule B): this is a cycle in the repair-dependency graph. What structurally prevents it is a **potential-function / lexicographic repair with a monotone measure**: define Φ = (number of violations, weighted violation area) and accept only repairs that do not increase Φ lexicographically; when no single-move repair decreases Φ, escalate to a larger neighbourhood (rip-up a whole group). This is the **feasibility-pump** discipline — repeatedly project onto the "rounding" (legal-grid) set and the "relaxation" (constraint) set. The feasibility pump is provably interpretable as a discrete version of the proximal-point algorithm, which is why random restarts / cutting planes escape the cycles that a naive alternating projection would loop in. In routing, the analogous anti-oscillation device is PathFinder's **history cost** (§4e): a resource repeatedly contested has its cost _permanently_ increased, so the negotiation cannot loop forever.

**(b) Minimal PEX subject to all constraints holding.**

The correct formulation is **lexicographic**, not scalarized:

```
lex-min  ( V(x) ,  Θ(x) ,  PEX(x) )
```

where V = total hard-constraint violation (DRC, LVS, exact equalities, disjunctions), Θ = total budget-constraint violation (coupling sums, thermal gradients, parasitic budgets, matching budgets), and PEX = the scalar parasitic objective (weighted R, C, coupling). Feasibility (V=0, Θ=0) **strictly dominates** PEX.

- **Why not a single scalarized objective** (min PEX + Σ w_i · violation_i): because with finite weights the optimizer will _trade matching/symmetry/thermal margin for parasitic reduction_ — exactly the "silently consuming margin" failure the brief warns about. A penalty that is finite is a bribe the optimizer will accept.
- **Why not a pure Pareto surface:** the analog problem is not "trade parasitics against matching" — matching is a _hard budget that must hold_, not a competing objective. Pareto is the wrong model above the feasibility frontier. It is only meaningful _within_ the PEX term (e.g., R vs C vs coupling), where a scalar weighting or a designer-set priority is appropriate.
- **Implementation:** augmented Lagrangian on the budget constraints Θ (soft → progressively enforced via rising ρ and updated multipliers λ), with PEX as the base objective. The canonical augmented-Lagrangian form L_ρ(x,λ) = f(x) − λᵀc(x) + (ρ/2)‖c(x)‖² is solved by alternating a primal minimization over x with a dual update λ ← λ − ρ·c(x). As ρ grows, budget constraints become effectively hard; the multiplier λ carries the "price" of each budget so PEX minimization cannot cross it. This is the RePlAce/DREAMPlace/ePlace augmented-Lagrangian machinery (also Zhu, Chen, Peng, Zhu & Chang's "generalized augmented Lagrangian and its applications to VLSI global placement," DAC 2018) repurposed from density to analog budgets. The free PEX oracle supplies exact constraint values every iteration, so λ updates use true residuals, not estimates.

**(c) LVS = true made structural, not merely checked.**

LVS equivalence must be an _invariant of the representation_, established two ways:

- **Connectivity by construction:** the netlist-to-geometry mapping is fixed by the generators and the router's net model; devices and nets are instantiated from the schematic, so device-count and net-count equivalence hold by construction. This is the ALIGN/MAGICAL guarantee.
- **The residual hazard is extraction ambiguity**: a placement move abuts two devices whose implants merge, so the _extractor_ sees one wrong/ambiguous device though the layout is perfectly DRC-legal. No downstream stage repairs this because nothing is "illegal." The structural defense is a **placement-time abutment/merge guard**: for every pair of same-layer diffusion/implant devices, maintain an invariant "either share-by-design (explicitly merged unit fingers) or keep the implant-merge keepout." Treat this as a _disjunctive constraint_ (§4b) exactly like the trench band. LVS is then called after any merging move to confirm the invariant held. The key insight the brief demands: LVS failure here is _created by placement_, so the fix must live in placement's legal-move definition, not in a post-route check.

### 4. The Hard Constraint Classes

**(a) Exact integer equalities (symmetry axes, integer ratios).** A penalty gradient on |x_i + x_j − 2·axis| converges to _near_-feasible and never _exactly_ feasible — the gradient vanishes only in the limit, and on an integer grid the optimizer parks one unit off. **Correct treatment: enforce by representation + projection, not by penalty.** Use a symmetric-feasible topological representation (Balasa–Lampaert symmetric-feasible sequence pair, which "can cover completely the set of all placements satisfying the common centroid and 1-D symmetry constraints"; ASF-B*-tree; or TCG-S) in which every decoded placement *exactly* satisfies the symmetry/centroid equalities by the decoding rule; the axis coordinate is a shared decision variable, and hierarchical/nested groups get nested sub-representations each with its own master axis (tail source on the axis). Integer ratios are enforced by **unitization**: the generator decomposes into identical integer unit counts so the ratio is exact by construction. The optimizer then searches *only over the feasible manifold\*, so "approaching arbitrarily closely" never arises. Matching budgets themselves follow Pelgrom: σ²(ΔP) ≈ A_P²/(W·L) for the random component (inversely proportional to gate area), plus a systematic gradient term rising with centre-to-centre separation — so the mismatch-voltage budget becomes a checkable inequality on gate area (set by variant/unitization) plus a separation penalty (set by placement), both exactly evaluable.

**(b) Disjunctive / non-convex feasible sets (deep-trench abut-or-separate band).** The feasible set is {d ≤ d_share} ∪ {d ≥ d_isolate} — two disconnected components with an illegal interval between. Penalty/gradient methods fall into the illegal gap. **Correct treatment: disjunctive programming / big-M with an explicit binary branch**, i.e., a per-pair Boolean b ∈ {share, isolate} that is a search variable; each branch is a convex (interval) constraint solved cleanly, and the outer search (branch-and-bound flavor, or an annealing move that flips b) explores both components. This is the standard "either-or" MILP modeling; the injector-exclusion (a device on a <1 kΩ path from a pad forced into a private ring) and implant-merge/LVS-guard constraints (§3c) are the same disjunctive shape. The free oracle prices each branch.

**(c) Set-level accumulating budgets (total coupling over all aggressors; two-sided area-weighted centroid).** No pairwise decomposition expresses "Σ over all aggressors ≤ budget" — a victim flanked by five minimum-spaced aggressors passes every pairwise rule and blows the budget 5×. **Correct treatment: keep the constraint as an explicit sum evaluated on the free PEX oracle over the victim's _whole neighbour set_, and put it in the augmented-Lagrangian layer with its own multiplier.** For the common-centroid two-sided property, enforce Σ_A a_i·(x_i−c) = Σ_B a_j·(x_j−c) = 0 as a _group-level_ linear equality in the representation (area-weighted centroid coincidence), which the common-centroid decoding (ABBA / checkerboard interleaving) satisfies structurally. Pairwise A–B enforcement is provably weaker (it does not deliver first-order gradient cancellation) and is explicitly rejected.

**(d) Constraints on derived state (thermal gradient on a placement-dependent field).** The temperature field T(x) is the solution of a Poisson-type PDE whose source term is the per-device power dissipation at current positions; every move changes the field. The constraint |T(dev_i) − T(dev_j)| ≤ ΔT_max is therefore a constraint on a _functional of the whole placement_, with tolerances ranging from ~2 °C for loose matching to 0.1 °C for bandgap references (BJT V_be drifts ~−2 mV/°C; MOSFET V_th −1 to −2 mV/°C). **Correct treatment: re-solve the field each epoch (fast, GPU-native FFT/stencil — §8) and treat the gradient constraint as a budget in the Lagrangian layer, with sensitivities obtained by the adjoint (one extra solve) or by finite differences over the free oracle.** For tight references the partners must sit on the _same isotherm_ — which the common-centroid/symmetry structure already tends to deliver, so the thermal constraint and the centroid constraint reinforce each other. The electrostatic-charge analogy used in thermal-aware placement (deriving the cost _change_ rather than re-extracting the full profile every iteration) lets the field-update cost be kept near-linear in device count per move; a full re-solve is reserved for per-epoch validation.

**(e) Constraints whose existence depends on placement (guard-ring sharing/geometry, injector exclusion).** A guard ring encloses a _placed_ bounding box; whether two requesters can share a ring depends on where placement put them, so the ring — simultaneously an obstacle and a net target — cannot be instantiated before placement, yet must exist before routing. **Correct treatment: a two-phase "instantiate-then-constrain" within each outer iteration.** After the middle-loop placement is provisionally fixed, _derive_ the ring grouping (same class/net/well + adjacency ⇒ shareable, unless one requester is an injector on a <1 kΩ path from a pad, which forces a private ring), draw the rings deterministically, and _then_ expose them to the router as both blockage and target. The ring set is **recomputed every iteration** because it is placement-derived state. This is a constraint that is _generated_ by the decision it constrains — handled by making ring derivation a deterministic function of placement, re-run each epoch, with LVS/DRC confirming enclosure completeness and the ~10 Ω ring-resistance budget via the PEX oracle.

### 5. Convergence and Termination

**Termination criterion ("cannot improve further"):** the incumbent is feasible (V=0, Θ=0, LVS true, zero DRC) **and** no move in the current neighbourhood structure — across _all three tiers_, including a full sweep of the collapsed variant space — reduces PEX by more than ε, **and** the augmented-Lagrangian multipliers have converged (‖λ\_{k+1} − λ_k‖ < δ, i.e., constraint prices are stationary). Feasibility alone is not termination; multiplier stationarity certifies that no budget is being actively traded.

**When monotone improvement can be guaranteed:** only _within_ a fixed variant assignment, a fixed topology, and a fixed active-constraint set, where the inner PEX minimization over the feasible manifold is a descent on a fixed objective (the lexicographic measure Φ then PEX is non-increasing under accepted moves — this is the anti-oscillation guarantee of §3a). Across variant/topology changes there is **no** global monotonicity; those are discrete jumps, handled by keeping the best incumbent and using acceptance criteria (annealing/replica exchange) that permit uphill moves.

**Escaping local minima, and distinguishing placement-local-minimum from variant-space-binding:** run **parallel tempering / replica exchange** over full layout replicas at different temperatures (§8) to escape placement basins. Replica exchange runs R chains at temperatures T₁<…<T_R and periodically swaps adjacent configurations with probability min{1, exp[(E_i − E_j)(β_i − β_j)]}, letting a stuck low-temperature replica escape via a high-temperature partner while preserving the correct stationary distribution. The critical diagnostic the brief asks for: _if the best feasible PEX cannot be improved by any position move but budget/feasibility violations persist across all replicas, the binding constraint is the variant space itself_ — no arrangement of the currently chosen variants can satisfy the constraints. The signature is: middle-loop feasibility residual Θ stalls at a positive floor that is invariant under position moves and temperature. The response is to force an outer-loop variant move (e.g., a higher-aspect-ratio or different metal-stack construction that changes pin geometry), which is detectable precisely because the oracle can certify "no local position move helps." This separation — position-infeasible vs variant-infeasible — is only cleanly diagnosable _because_ the oracle is free and can exhaustively test the local neighbourhood.

### 6. Constraint Weighting and Enforcement

- **Classification (hard/strict-legality vs soft/objective-pressure):** DRC, LVS, exact equalities, disjunctions, and ESD bus-resistance (a >100 A/<1 ns event makes the pad-to-clamp resistance budget physically hard) are **strict-legality** — enforced by construction/projection/branching. Budgets (coupling sum, thermal gradient, parasitic R/C, matching-voltage) start as **objective-pressure** and are _ramped to effectively hard_ via the augmented-Lagrangian penalty ρ and multipliers λ.
- **Can classification legitimately change during the run? Yes, and it should.** A matching budget that is comfortably satisfied can stay soft (cheap); one that becomes binding is promoted (ρ raised) so it is protected. This is the adaptive-penalty discipline: increase ρ for constraints whose residual is not shrinking, decrease pressure on those with slack. The multiplier λ_i is precisely the _shadow price_ of constraint i and tells you which constraints are actually binding.
- **Stopping soft objectives from being traded away entirely once a hard constraint dominates:** the lexicographic structure (§3b) prevents PEX from ever buying its way past a hard constraint, and a _floor_ on the PEX weight ensures that among feasible configurations the parasitic objective is never zeroed out — feasibility does not license arbitrary parasitics.
- **Stopping hard-constraint repair from thrashing:** the monotone lexicographic measure Φ plus PathFinder-style history costs on contested resources (routing) and rising ρ (placement) guarantee that repeatedly contested constraints get monotonically more expensive, so repair converges instead of oscillating.

### 7. Where the Leverage Is (ranked by expected DRC/PEX/LVS improvement ÷ implementation difficulty)

1. **Exact-by-construction representation for symmetry/centroid/integer-ratio (highest leverage, moderate difficulty).** Converts an entire class of never-quite-feasible penalty failures into structural guarantees. Directly delivers LVS-relevant structure and matching. Well-trodden (sequence-pair/B\*-tree/TCG literature) so difficulty is bounded. This single choice removes the largest source of "converges near-feasible" failure.
2. **Free-oracle-in-the-loop feasibility pump with lexicographic objective (high leverage, moderate difficulty).** This _is_ the answer to the central question and is what makes zero-DRC/LVS-true _certain_ rather than seed-dependent. Difficulty is mostly in the bookkeeping (multipliers, Φ, acceptance), not in new math.
3. **Set-level budget handling via oracle sums + multipliers (high leverage, low-moderate difficulty).** Fixes the coupling-budget and centroid failures that pairwise rules cannot express; cheap because the PEX oracle already returns the needed sums.
4. **Disjunctive branching for trench/injector/merge constraints (medium leverage, low difficulty).** Small, well-understood MILP-style modeling; prevents a specific but fatal class of illegal-gap parking and LVS extraction ambiguity.
5. **Thermal-field-in-the-loop with adjoint sensitivities (medium leverage, medium-high difficulty).** Needed for references; the PDE re-solve is the cost, mitigated by GPU (below).
6. **GPU rewrite (variable leverage, high difficulty — see §8).** _Not_ a correctness lever; a throughput lever. Its ranking is deliberately below the algorithmic items because a faster wrong loop is still wrong. Its value is that it makes the batched-oracle and replica-exchange strategies (which _do_ improve solution quality by exploring more) practical. Ranked here because the highest-value GPU targets (batched evaluation, thermal/electrostatic FFT) are moderate-difficulty and high-throughput-payoff, while the lowest-value ones (GPU detailed routing) are high-difficulty and low-payoff.

The reasoning behind this ordering: interventions 1–4 change _whether the answer is correct at all_ (feasibility certainty), and correctness is worth more than speed; among them the ordering tracks how large a failure class each removes per unit of engineering. Intervention 5 is gated by a narrower (but critical) circuit class (references). Intervention 6 multiplies the _rate_ at which 1–5 explore but cannot substitute for them.

### 8. GPU Parallelization of OpenROAD-Derived Components — Work-Span Analysis

**Prior question first (deliverable 8k): is extending OpenROAD even the right basis?** _Partially._ The analog problem's hard constraint classes (exact equalities, disjunctions, set-level budgets, placement-derived constraints) are **not** what OpenROAD's digital flow is built for; the topological-representation + oracle-feedback core recommended above is analog-specific and is **not** an OpenROAD component. However, several OpenROAD-derived _sub-computations_ are genuinely reusable and worth GPU analysis: (i) ePlace/RePlAce electrostatic global placement (for a coarse initial spread and because its FFT Poisson solve is structurally identical to the thermal solve we need anyway); (ii) TritonRoute-style negotiated detailed routing (for the actual wires); (iii) global routing; (iv) DRC geometry. We scope the GPU analysis to those.

**Hardware assumption:** a single modern discrete CUDA-class GPU (e.g., A100/H100-class, ~40–80 GB HBM). All primitives named (map/scan/segmented-scan/compaction/scatter/histogram/radix-sort/reduce-by-key/stencil/frontier-expansion/work-queues) have ROCm/HIP equivalents (rocPRIM/hipCUB, rocFFT, rocBLAS) so vendor portability is preserved. Established libraries preferred: **cuFFT** (Poisson/thermal), **CUB/Thrust** (scan/sort/reduce/compaction), **cuSPARSE/cuBLAS** (field solves), **CUTLASS** (dense variant-batch scoring).

#### (a) Contract and equivalence level per stage

| Stage                                                               | Inputs → Outputs            | Mutated state                 | Required order                 | **Equivalence level required**                                                                                                             |
| ------------------------------------------------------------------- | --------------------------- | ----------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Exact legality checks (symmetry axis, integer ratio, LVS structure) | layout → bool/violation set | none                          | none                           | **Bitwise / exact-arithmetic** — integer equalities; a reduction-order or float error that flips a boundary comparison corrupts the answer |
| DRC geometry                                                        | layout → violations         | none (pure)                   | none                           | **Exact** on integer grid coordinates (sweepline comparisons are exact-integer)                                                            |
| Electrostatic global placement (ePlace)                             | net/cell data → positions   | positions, density, potential | Nesterov step order            | **Numeric-within-tolerance** — trajectory need not be bitwise; converged result matters                                                    |
| Thermal field solve                                                 | power map → T field         | field buffer                  | none (pure solve)              | **Numeric-within-tolerance**                                                                                                               |
| Annealing / replica exchange                                        | state → state               | RNG, energy                   | Metropolis chain order (see i) | **Statistical** — trajectory may differ; stationary distribution / best-found must be preserved                                            |
| PEX (field-solver / random-walk)                                    | layout → R,C,coupling       | none (pure)                   | none                           | **Numeric-within-tolerance** (random-walk is statistical)                                                                                  |
| Detailed routing                                                    | guides → wires              | routing DB, congestion        | net order (negotiated)         | **Application-semantic** — must be DRC-clean and connected; exact path may differ                                                          |

**Consequence of GPU nondeterminism:** atomic-ordering and tree-reduction reordering make floating sums non-reproducible (float + and × are non-associative). This is **acceptable** for placement gradients, PEX, and annealing energies (tolerance/statistical), but **forbidden** for the exact legality/LVS/symmetry checks and for integer-grid DRC comparisons — those must use integer arithmetic or a deterministic reduction so that _signoff results are reproducible_. The rule: **any oracle output that gates a hard-constraint decision must be computed deterministically; any output feeding only an objective/gradient may be nondeterministic.** This cleanly partitions the engine.

#### (b)–(e) Dependency DAGs, artificial-edge cuts, and parallel dimensions

**ePlace/RePlAce global placement.** Per Nesterov iteration the dependency chain is: wirelength+density gradient → step → new positions → new density → FFT Poisson solve → new potential/field → next gradient. The **span** is iteration-count × (FFT depth + reduction depth). Most intra-iteration edges are _data-parallel maps and reductions_ (per-cell, per-bin), not true sequential dependencies — the only true RAW chain is iteration-to-iteration (mathematically required: it is an optimizer). The FFT is O(n log n) work, O(log n) span, a **cuFFT** call. Density accumulation is a **histogram/scatter** (count–scan–scatter via CUB replaces a global accumulator to cut the counter-induced anti-dependency). This is exactly DREAMPlace's insight: cast placement as a neural-network-training computation over cuFFT + dense ops, with Nesterov's method (line-search resolved via a closed-form Lipschitz-constant steplength). **Verdict: nested-parallel** (sequential outer optimizer, massively parallel inner) — DREAMPlace already realizes this, but the win requires large n.

**Thermal field solve.** Identical structure to the ePlace Poisson solve: a stencil/FFT PDE on a grid. **cuFFT** for the fast Poisson solve (uniform grid) or a **cuSPARSE** conjugate-gradient (as in HotSpot-style thermal solvers) for variable conductivity; adjoint for sensitivities is a second identical solve. **Work** O(g log g) for grid g; **span** O(log g). Pure function, re-run per epoch. **Verdict: strong GPU fit** — a native stencil/FFT workload, and it must be recomputed as devices move, so it amortizes.

**Simulated annealing / the Metropolis chain (deliverable 8i).** The serial dependence between accepted moves is the classic obstruction. Three treatments, in order of correctness-safety:

- _Replica exchange / parallel tempering_ — R independent chains at different temperatures with periodic Metropolis swaps. **Embarrassingly parallel across replicas**; the swap is a cheap reduction. This is the _recommended_ population-based GPU strategy. Known caveat: parallel tempering preserves the stationary distribution (unbiased) but needs energy-distribution overlap between adjacent temperatures for good swap acceptance; GPU Potts-model parallel-tempering implementations demonstrate the pattern and its ladder-tuning requirement.
- _Batched speculative moves with conflict detection_ — propose many moves at once, evaluate all with the free oracle in parallel, then commit a non-conflicting independent set (exactly ABCDPlace's batch-independent-set discipline for detailed placement: independent set matching, global swap, local reordering made concurrent). Introduces bias if committed naively; the conflict-detection/independent-set step restores correctness.
- _Parallel SA with speculative acceptance_ — known in the literature to introduce bias in the accepted-move distribution; use only with correction.
  **Verdict: weakenable** (the chain is real but reorderable/groupable into replicas and batched proposals) — this is the single biggest GPU lever for _this_ engine.

**Sequence-pair / B\*-tree packing evaluation.** The packing (longest-path in a constraint graph / LCS for sequence pair) is a DP whose CPU form is sequential. It is a **longest-path over a DAG by level sets** — parallelizable by scan over topological levels (the same node-level parallelism InstantGR exploits for routing DAGs). **Work** O(n²) worst case, **span** reducible toward O(log²n) with parallel prefix. At analog n (tens–hundreds), this is **thin** — the constraint graph is too small to fill a GPU; keep on CPU, or run _many_ candidate packings in parallel (batch over annealing replicas), which is where the parallelism actually lives.

**Global routing (deliverable 8j).** This _does_ transfer. GAMER (Lin, Liu, Young, Wong, IEEE TCAD 42(2):583–593, Feb 2023) reformulates the multisource–multidestination shortest path as alternating horizontal/vertical **sweep** operations, accelerating a sweep from O(n²) to O(log²n) on an n×n grid; integrated into CUGR, "coarse-grained routing and fine-grained routing… can be accelerated by 19.85× and 2.59×, respectively, with GAMER, achieving an overall speedup of 2.7× without quality degradation." InstantGR (Xiao, Lin, Liu, Duan, Ho, Young, ICCAD 2024 / IEEE TCAD 2026) adds **node-level parallelism** (routing-DAG nodes of equal depth in parallel) and, per the project's own reporting, "achieves 2.16× speedup and a 1.6% quality improvement over the contest winner" on ISPD'24 benchmarks (with node-level parallelism averaging ~10.7× over the traditional net-level strategy). FastGR (Liu et al., DATE 2022 / IEEE TCAD 2023) combines GPU pattern routing with a heterogeneous CPU-GPU task-graph scheduler for ~10.9× on GPU. **Verdict: weakenable/nested-parallel — adopt GAMER/InstantGR-style formulations for the global-routing stage.**

**TritonRoute-style detailed routing (deliverable 8j).** This does **not** transfer well. Detailed routing resists GPU acceleration for three structural reasons the literature confirms: (i) exponentially-growing irregular design rules (parallel-run-length spacing, end-of-line, corner-to-corner) that make per-thread work divergent; (ii) the sequential net-by-net rip-up-and-reroute dependency (TritonRoute uses a queue-based rip-up-and-reroute with A* search inside per-worker "standard boxes"); (iii) path-search warp divergence. The GPU EDA literature accelerates global routing, track assignment, layer assignment, and DRC — but mainstream detailed routing remains CPU-bound (TritonRoute's own parallelism is *intra-layer parallel panels\* on CPU with an ILP-based per-panel algorithm; Dr. CU similarly uses CPU concurrency). **Verdict: thin / movement-bound — keep detailed routing on multi-threaded CPU; use the GPU for the DRC oracle that scores its output.** This is a legitimate "belongs on the CPU" outcome.

**Negotiated rip-up-and-reroute ordering (PathFinder).** McMurchie & Ebeling (ACM FPGA 1995, pp. 111–117) give the cost of using node n as **c_n = (b_n + h_n)·p_n**, where "b_n is the base cost of using n, h_n is related to the history of congestion on n during previous iterations… and p_n is related to the number of other signals presently using node n." Present congestion p_n resolves first-order contention (raised gradually so signals "negotiate" rather than being blocked by an infinite cost); "the effect of h_n is to permanently increase the cost of using congested nodes," which is precisely the **anti-oscillation / convergence guarantee** — a repeatedly contested resource becomes monotonically more expensive until routes diverge. This maps directly onto our placement thrash-prevention (§6) and onto **batched concurrent routing with cost-based conflict resolution** on GPU: route many nets concurrently against a shared cost field, detect over-capacity resources by **histogram/reduce-by-key**, update h_n and p_n, repeat. **Verdict: weakenable** — the negotiation is inherently iterative but each iteration is data-parallel over nets and resources.

**DRC geometry oracle.** X-Check (Su, Meng, Yu et al., ICCAD 2022, parallel sweepline) "achieves up to 1257.76× speedup, with an average of 61.36×" vs KLayout (8 threads), and "up to 280.66×… average of 45.00×" on space checks. OpenDRC (DAC 2023) adds hierarchical GPU acceleration and beats X-Check ~4.5× on average. General GPU scanline DRC (Zhong, Feng et al., DATE 2023) reports, "compared with the baseline with 24 threads… an average speedup of 36× and 201× for spacing rule checks and enclosing rule checks on a metal layer, respectively." **Verdict: strong GPU fit** — the batched DRC oracle is a native win, and it is exactly the oracle we call most often. Must use a **deterministic** integer sweepline so signoff is reproducible (per §8a).

**PEX oracle.** Fast-multipole (FastCap-style) capacitance extraction on GPU: FMMGpu (Zhao & Feng, DAC 2011) reports 22–30× vs serial CPU; GPU-friendly floating random walk (DATE 2013) reports over 20× per net and up to 59× for multi-net extraction. **Verdict: GPU fit, statistical equivalence** — random-walk is inherently statistical, acceptable for the objective/budget terms; use variance control so coupling-budget decisions are stable.

#### (f) Candidate comparison and (h) the critical workload-size question

For each component we compared (per deliverable 8f) three formulations — minimal transformation, aggressive reformulation, higher-work-but-more-regular — on work W, span S, W/S, memory traffic, temporaries, kernel launches, global syncs, atomic contention, divergence, load balance, determinism, and _useful input range_. The decisive axis for this engine turned out to be **useful input range**, not span:

**The decisive analysis (deliverable 8h):** at analog device counts (tens–thousands, not DREAMPlace's millions), **single-trajectory GPU placement is "thin."** The parallel slack in one placement iteration is a few thousand cell-updates at most — below the threshold where GPU compute beats kernel-launch (~5–20 µs each) plus host–device transfer. A single-trajectory analog placer should stay on CPU or use the GPU only for its FFT/thermal solve.

**Where the GPU leverage actually is** — the crossover from "clever incremental CPU bookkeeping" to "brute-force batched full recompute on GPU" — sits exactly where the free oracle lets us **replace one incremental update with thousands of parallel full evaluations**:

1. **Batched candidate-move / variant-hypothesis evaluation.** Score thousands of hypothetical moves/variants/layouts in parallel with GPU DRC/PEX/thermal kernels. Work is higher (full recompute per candidate) but span is short and the hardware is saturated _because the batch dimension supplies the parallelism the single design lacks_. This is the analog-specific inversion of ABCDPlace's batch-concurrency idea, and it is the primary recommendation.
2. **Parallel tempering over full layout replicas.** R replicas fill the GPU even when one design does not; unbiased and quality-improving.
3. **The two field solves (electrostatic density + thermal PDE)** via cuFFT/cuSPARSE — native, amortized, and the thermal one is _required anyway_ by the gradient constraint.

**Crossover rule of thumb:** batch full-recompute on GPU wins when (batch size × per-candidate work) exceeds ~10⁵–10⁶ independent element-operations, i.e., when you are evaluating hundreds-plus candidates or dozens-plus replicas simultaneously; below that, incremental CPU update wins. Because the oracle is a pure function and free, the batch dimension is always available — so the engine should be architected to _always_ have many candidates in flight, precisely to keep the GPU above crossover.

**GPU-accelerated analog P&R literature: essentially nonexistent.** The GPU EDA literature (DREAMPlace 1–4, Xplace, ABCDPlace, GAMER, FastGR, InstantGR, X-Check, OpenDRC, FMMGpu) is entirely _digital_ placement/routing/verification and _device-count-large_. There is no GPU-accelerated analog P&R engine in the literature. The batched-oracle and replica-exchange architecture above is therefore **derived from first principles**, and its failure modes are named: (i) if per-candidate oracle work is too small, the batch never reaches crossover and the GPU idles (thin); (ii) random-walk PEX variance can make budget decisions flap unless variance-controlled; (iii) nondeterministic reductions must be quarantined from hard-constraint gating or signoff becomes irreproducible; (iv) parallel-tempering swap acceptance collapses without temperature-ladder tuning; (v) batched speculative moves bias the search unless a conflict-detection/independent-set commit step is used.

#### (g) Named verdicts, summarized

- ePlace/RePlAce global placement — **nested-parallel** (win only at large n; thin at analog sizes for a single trajectory).
- Thermal / electrostatic Poisson solve — **strong GPU fit / needs-the-math-we-already-have** (cuFFT/cuSPARSE).
- Metropolis annealing chain — **weakenable** (replica exchange + batched proposals with conflict detection).
- Sequence-pair / B*-tree packing — **thin** at analog n (parallelize the *batch\* of candidates, not one packing).
- Global routing (GAMER/InstantGR/FastGR) — **weakenable / nested-parallel** (adopt).
- Detailed routing (TritonRoute-style) — **thin / movement-bound** (stay on CPU).
- PathFinder negotiation — **weakenable** (data-parallel per iteration).
- DRC oracle — **strong GPU fit** (deterministic integer sweepline).
- PEX oracle — **GPU fit, statistical** (variance-controlled).
- Batched candidate/variant/replica evaluation — **the primary GPU win, derived from first principles.**

## Recommendations

**Stage 1 — Build the correctness core (do first, CPU):**

- Adopt a symmetric-feasible topological representation (sequence-pair or ASF-B\*-tree/TCG-S) so symmetry axes, hierarchical symmetry groups, common-centroid, and integer ratios are **exact by construction**. Benchmark: zero symmetry/centroid residual on a differential-pair + current-mirror + bandgap testbench.
- Implement the lexicographic feasibility-pump middle loop with augmented-Lagrangian budgets and the monotone Φ anti-oscillation measure. Wire the free DRC/PEX/LVS oracles as per-move / per-epoch signals. Benchmark: certain zero-DRC and LVS-true on _every_ seed (not just one), with PEX monotonically non-increasing within a fixed variant assignment.
- Handle disjunctive constraints (trench, injector, implant-merge/LVS guard) by explicit binary branching; handle set-level budgets (coupling sum, two-sided centroid) as oracle-evaluated sums with multipliers.

**Stage 2 — Cell-awareness and search quality:**

- Implement group-coupled variant collapse + oracle pricing; allow variant swaps as outer-loop moves. Benchmark: detect and repair a variant-space-binding case (feasibility floor invariant under position moves) by an automatic variant escalation.
- Add parallel tempering over full replicas for basin escape.

**Stage 3 — GPU throughput (only after Stages 1–2 are correct):**

- Port the **DRC oracle** (deterministic integer sweepline, X-Check/OpenDRC-style), the **PEX oracle** (FMM or floating random walk, variance-controlled), and the **thermal + electrostatic field solves** (cuFFT/cuSPARSE) to GPU. Architect the loop to keep **hundreds of candidates / dozens of replicas** in flight so the batch dimension keeps the GPU above crossover.
- Adopt **GAMER/InstantGR-style GPU global routing**; keep **detailed routing on multi-threaded CPU** with the GPU DRC oracle scoring its output.
- **Do not** invest in single-trajectory GPU placement or GPU detailed routing — both are thin at analog sizes.

**Thresholds that change these recommendations:** if a design grows past ~10⁴–10⁵ devices (large arrays/DACs), single-trajectory GPU placement (DREAMPlace-style) crosses back into "worth it." If detailed-routing DRC-clean closure becomes the bottleneck rather than search quality, revisit CPU-panel parallelism before attempting GPU detailed routing. If PEX-budget decisions flap, raise random-walk sample counts (trading GPU work for variance) before changing the algorithm.

## Caveats

- **No published system operates in the free-oracle regime**; the core loop is derived from first principles by composing established components (symmetric-feasible representations, augmented Lagrangian/feasibility pump, PathFinder negotiation, parallel tempering) in a new configuration. The composition is argued, not empirically validated here.
- **Speedup figures are from digital, large-count benchmarks** (DREAMPlace >30×/~40×, ABCDPlace >16×, GAMER 2.7× overall, InstantGR ~2.16× over the ISPD'24 contest winner, FMMGpu 22–30×, X-Check up to 1257.76× avg 61.36×, GPU scanline DRC 36×/201×). They establish _that_ the primitives parallelize; they do **not** predict analog-size performance, which the "thin" analysis explicitly cautions is worse for single trajectories.
- **Reported InstantGR headline numbers vary slightly by source/version** (conference vs. journal vs. repository: ~2.0–2.16× over the contest winner, ~10.7× node- vs net-level); treat the exact multiplier as version-dependent.
- **Parallel/speculative SA can bias the search**; only replica exchange (with tuned temperature ladders) and batched proposals with conflict-detection commits are treated as correctness-safe here.
- **GPU nondeterminism must be quarantined** from any hard-constraint or LVS/signoff decision; failing to do so makes results irreproducible even when "correct on average."
- Some cited items are preprints or vendor materials (e.g., recent arXiv routing work, Pulsic product descriptions) and should be treated as lower-evidence than peer-reviewed TCAD/DAC/ICCAD papers.
