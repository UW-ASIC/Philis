# 1.2 Data Structures for Rectilinear Border Contours

> **Chapter 1**: Device-Level Topological Placement with Symmetry Constraints (Florin Balasa)
> **Part**: Part I: Placement

## Key Concepts

This section addresses a core computational sub-problem in analog placement: **how to efficiently track the rectilinear (staircase-shaped) right border contour** of a partially-placed layout as devices are added one by one. The border contour must be maintained so that each new device can be pushed as far left as possible without overlapping existing devices -- this is the mechanism that converts a topological ordering into actual $(x, y)$ coordinates.

### The Placement Evaluation Problem

Given:
- A set of $n$ rectangular devices $B_1, \ldots, B_n$ with widths $w_i$ and heights $h_i$.
- The $y$-coordinates (ordinates) $y_i$ of each device (already computed or known).
- A **topological sort** of the horizontal constraint graph derived from the [[1.3 Symmetric-Feasible Sequence-Pairs|topological representation]] (e.g., sequence-pair).

The task is to compute the $x$-coordinates (abscissae) $x_i$ for each device, such that devices are packed leftward respecting the horizontal ordering constraints. The key insight is that the **right border contour** of the partial placement is a rectilinear (staircase) polyline, and each new device $B_i$ must be placed at the rightmost $x$-value among the contour segments it overlaps vertically (in the $y$-span $[y_i, y_i + h_i]$).

### Why Data Structure Choice Matters

The naive approach of checking all previously placed devices for each new device yields $O(n^2)$ evaluation. Since this evaluation is called in the **inner loop** of a simulated annealing optimizer (potentially millions of times), reducing the per-evaluation cost from $O(n^2)$ to $O(n \log n)$ has major practical impact. Four data structures are presented, all achieving $O(n \log n)$ total time with $O(n)$ space, but differing in constant factors, implementation complexity, and behavior when embedded in an annealing loop.

## 1.2.1 Segment Trees

A **segment tree** is a balanced binary tree used to store and query interval data. In this context, the $y$-axis is discretized into a set of elementary intervals based on the sorted, deduplicated set of $y$-coordinates:

$$S = \bigcup_{i=1}^{n} \{y_i,\; y_i + h_i\}$$

After sorting and deduplication, $S$ has $m \leq 2n$ elements. These elements partition the $y$-axis into elementary intervals. A **normalization** step maps these values to indices $\{0, 1, \ldots, m-1\}$, reducing the tree depth from $\lceil \log_2 H \rceil$ (where $H$ is the chip height) to $\lceil \log_2 m \rceil$.

**Node structure:** Each node $v$ in the segment tree stores:
- $v.I = [a, b]$: the normalized interval it represents.
- $v.x$: the maximum $x$-value (abscissa of the rightmost contour segment) in this interval.
- $v.\text{leaf}$: a flag indicating if this is currently a leaf node.

**Algorithm sketch (per device $B_i$):**
1. **Query phase** (`UpdateSegmentTree`): Walk the tree to find the maximum $v.x$ over all nodes whose intervals overlap with $[y_i, y_i + h_i]$ (after normalization). This maximum becomes $x_i$.
2. **Update phase** (`UpdateRightContour`): Update the contour by setting the $x$-value to $x_i + w_i$ for the portion of the contour covered by $[y_i, y_i + h_i]$.

The tree walk identifies a **fork node** where the query interval splits into left and right paths ($P_L$ and $P_R$). The maximum is collected along both paths. Standard segments (nodes whose intervals are fully contained in the query) are marked with double circles; fork nodes are marked with a star.

**Optimization for simulated annealing:** The segment tree should be created **only once** at the start of the annealing process with root interval $[0, n]$, since all per-iteration root intervals $[0, k]$ where $k \leq n$ are subsets. Only node flags and $x$-values need to be re-initialized per iteration, not the tree structure itself. Failing to exploit this increases computation time by **15--20%**.

**Complexity:** $O(n \log n)$ time, $O(n)$ space per evaluation.

## 1.2.2 Red-Black Interval Trees

A **red-black interval tree** is a self-balancing binary search tree where each node stores a closed interval representing a segment of the border contour. The key properties are:

- **Interval disjointness:** The interior of each node's interval is disjoint from all others, and their union covers $[0, H]$ (the full chip height).
- **Sorted order:** An in-order traversal lists intervals sorted by their low endpoints.
- **Red-black balancing:** Each node is colored red or black, with the constraints that (1) red nodes have only black children, and (2) every root-to-leaf path has the same number of black nodes. This ensures no path is more than twice as long as any other, giving $O(\log n)$ height.

**Node structure:** Each node $v$ stores:
- $v.I$: the interval $[\min\{v.I\}, \max\{v.I\}]$ on the $y$-axis.
- $v.x$: the abscissa of the vertical contour segment at this $y$-interval.
- Color: red or black.

### The Interval Trichotomy

When inserting a new device's $y$-span $[a, b] = [y_i, y_i + h_i]$ into the tree, the procedure `UpdateRedBlackTree` handles the relationship between the existing node interval $v.I$ and $[a, b]$ via three cases:

- **(a)** $\max[a, b] \leq \min\{v.I\}$ -- the new interval is entirely left; recurse left.
- **(b)** $\max\{v.I\} \leq \min[a, b]$ -- the new interval is entirely right; recurse right.
- **(c)** The interiors overlap -- four sub-cases arise (see figure below):
  - **(c1)** $[a,b]$ overlaps the left portion of $v.I$: shorten $v.I$ from the left, recurse left.
  - **(c2)** $[a,b]$ overlaps the right portion of $v.I$: shorten $v.I$ from the right, recurse right.
  - **(c3)** $v.I$ contains $[a,b]$: fragment $v.I$ into up to 3 pieces -- this is the only case that **increases** the node count (by at most 2).
  - **(c4)** $[a,b]$ contains $v.I$: delete all nodes with intervals fully covered by $[a,b]$ -- this can remove up to $O(n)$ nodes in the worst case.

![[assets/ch1-interval-trichotomy-034.png]]
**Fig. 1.6:** The interval trichotomy for two possibly-overlapping closed intervals $v.I$ and $[a, b]$, showing the three main cases and the four overlap sub-cases (c1--c4). Below the figure is the full pseudocode for `UpdateRedBlackTree`.

### Merging Adjacent Intervals

After each update, `MergeAdjacentIntervalsWithSameAbscissae` checks if the updated node's interval is adjacent to a neighbor with the same $x$-value. If so, the intervals are merged (the neighbor is deleted) to keep the contour representation minimal. This avoids accumulating redundant collinear segments.

### Amortized Complexity Analysis

Although a single iteration can delete $O(n)$ nodes (case c4), the **amortized cost** per iteration is $O(\log n)$ by the aggregate method: each node can only be deleted once for each time it was created, and at most 2 nodes are created per iteration (case c3). Over $n$ iterations:

$$\text{Total cost} = O(n \log n)$$

**Space:** $O(n)$, since the tree has at most $2n - 1$ nodes (the number of vertical segments of the right border contour).

### Why Red-Black Over AVL?

AVL trees achieve the same asymptotic complexity, but require up to $\Theta(\log n)$ rotations after a deletion. Red-black trees need at most **2 rotations** after insertion and **3 after deletion**, making them more efficient in practice despite being only approximately balanced.

## 1.2.3 Deterministic Skip Lists

### Background: Probabilistic Skip Lists (PSL)

A **probabilistic skip list** (Pugh, 1990) stores keys in multiple sorted linked lists at increasing levels. All keys reside at level 1; each key at level $k$ is promoted to level $k+1$ with probability $p$ (typically $p = 1/2$). Searching starts at the highest level and drops down, yielding an **expected** search cost of:

$$\frac{1}{p} \log_{1/p} n$$

**Problem:** While the PSL has $O(\log n)$ average time, its worst case is $O(n)$ time and $O(n \log n)$ space -- unacceptable if the random number generator behaves poorly.

### Deterministic Skip Lists (DSL)

A **deterministic skip list** (Munro et al.) replaces randomization with a **gap invariant**. The **gap size** between two linked elements at height $h$ is the number of nodes at height $h-1$ between them.

**Key theorem:** There is a one-to-one mapping between B-trees of order $m \geq 3$ and DSLs with gap sizes in $\{\lceil m/2 \rceil - 1, \lceil m/2 \rceil, \ldots, m-2, m-1\}$. This guarantees **logarithmic worst-case** complexity for search and update.

The simplest practical DSL is the **1-3 DSL** (also called 1-2-3 DSL), where all gap sizes are in $\{1, 2, 3\}$. It corresponds to a 2-3-4 tree (B-tree of order 4) and supports top-down insertion and deletion.

### 1.2.3.1 Insertion in a 1-3 DSL

**Top-down approach:** Starting from the header at the highest level:
1. If the gap we are about to drop into has size 1 or 2, simply drop.
2. If the gap has size 3, **raise the middle element** to create two gaps of size 1, then drop.
3. At the bottom level, insert the new key as a height-1 node.

This pre-emptive splitting ensures the gap invariant is maintained regardless of whether the key is ultimately inserted.

### 1.2.3.2 Deletion from a 1-3 DSL

**Top-down approach:** Starting from the header:
1. If the gap to drop into has size 2 or 3, simply drop.
2. If the gap has size 1:
   - If the **next gap** $G'$ has size 1: **merge** by lowering the separating element.
   - If $G'$ has size 2 or 3: **borrow** -- lower the separator, raise the first element of $G'$.
   - If this is the last gap: merge/borrow from the preceding gap.
3. At level 1, remove the key (swap with predecessor if height > 1).

This ensures no gap of size 1 remains before the removal, keeping the DSL valid.

### 1.2.3.3 Implementation Details

The **linked list implementation** is preferred over horizontal arrays. Each `DslNode` stores:
- `key`: the $y$-coordinate where the contour changes direction.
- `x`: the abscissa of the border segment starting at this $y$-coordinate.
- `down`: pointer to descend one level.
- `right`: pointer to the next node on the same level.

Sentinel nodes `head`, `tail`, and `bottom` replace NULL pointers. A node at height $h$ in the abstract DSL appears as $h$ `DslNode` objects in the implementation, each storing the same key.

**Why not arrays of forward links?** Promoting a height-$h$ node to $h+1$ would require $O(h)$ time to copy links, degrading the bound to $O(\log^2 n)$.

### 1.2.3.4 Algorithm for Border Contour Computation

![[assets/ch1-dsl-contour-044.png]]
**Fig. 1.13:** (a) How the right border contour is modified when a new block $B_i$ with $y$-span $[y_i, y_i + h_i]$ is processed. The contour segments between $y_j$ and $y_k$ are replaced. (b) The final device placement corresponding to the last 1-3 DSL state after all devices are placed.

The DSL keys represent the $y$-coordinates where the contour changes direction. For each device $B_i$ with $y$-span $[a, b] = [y_i, y_i + h_i]$:

1. Find node $q$ with the largest key $\leq a$ (i.e., the contour segment starting at or below $a$).
2. Set $x_i = \max\{p.x\}$ for all nodes $p$ with keys in $[q.\text{key}, b)$ -- the device must clear all overlapping contour segments.
3. Insert key $b$ if not present (inheriting the $x$-value of its predecessor).
4. Insert key $a$ if $q.\text{key} < a$.
5. Remove all keys in the open interval $(a, b)$ -- these contour segments are now hidden behind device $B_i$.
6. Set $\text{DslNode}(a).x = x_i + w_i$.
7. **Merge adjacent collinear segments:** if $\text{DslNode}(a).x = \text{DslNode}(b).x$, remove $b$; if the predecessor of $a$ has the same $x$-value, remove $a$.

**Amortized complexity:** $O(\log n)$ per iteration (same aggregate argument as red-black trees: each key deleted at most once per insertion). Total: $O(n \log n)$.

**Space:** $O(n)$ -- at most $n + 1$ elements in the DSL, and at most $2n + 7$ `DslNode` objects in the linked list implementation (accounting for all levels plus sentinel nodes).

## 1.2.4 Johnson's Priority Queue

**Johnson's priority queue** is designed for integer keys in $\{1, \ldots, N\}$. Its structure:

- $N$ **buckets**, one per possible key value. Only nonempty buckets (plus bucket 0 as a permanent header) are maintained.
- The nonempty buckets form a **doubly-linked bucket list**, sorted by key values.
- The buckets correspond to the **leaves** of a binary tree $T$. The nodes of $T$ are indexed via a **complete host binary tree** $H = \{1, \ldots, 2^h + N\}$, where $h = \lceil \log_2(N + 1) \rceil$. Each node $q$ in $H$ (except the root) is a child of node $\lfloor q/2 \rfloor$.

This structure enables efficient priority queue operations (insert, delete-min, decrease-key) for the border contour tracking problem when the keys are bounded integers.

## Algorithms & Methods

### Summary Comparison of All Four Data Structures

| Data Structure | Time (total) | Space | Worst-case per iteration | Amortized per iteration | Notes |
|---|---|---|---|---|---|
| **Segment Tree** | $O(n \log n)$ | $O(n)$ | $O(\log n)$ | $O(\log n)$ | Best with SA (create once, re-init per iteration) |
| **Red-Black Interval Tree** | $O(n \log n)$ | $O(n)$ | $O(n)$ (case c4) | $O(\log n)$ | At most 2n-1 nodes; few rotations |
| **1-3 DSL** | $O(n \log n)$ | $O(n)$ | $O(n)$ (mass deletion) | $O(\log n)$ | Top-down insert/delete; linked list impl. |
| **Johnson's PQ** | $O(n \log n)$ | $O(n)$ | -- | $O(\log n)$ | Integer keys only; bucket + binary tree |

### Common Algorithmic Pattern

All four data structures implement the same abstract operation:
1. **Query:** Given a new device's $y$-span $[y_i, y_i + h_i]$, find the maximum $x$-value among all contour segments overlapping this span. This becomes $x_i$.
2. **Update:** Replace the overlapping contour segments with a single segment at $x_i + w_i$ over $[y_i, y_i + h_i]$, merging adjacent segments with equal $x$-values.

### Amortized Analysis (Aggregate Method)

For the red-black tree and DSL, the key amortized argument is:
- Each contour segment (node/key) is created at most once per device insertion (at most 2 new segments per iteration in the overlap cases).
- Each segment can be deleted at most once.
- Therefore, over $m$ operations, at most $O(m)$ insertions and $O(m)$ deletions occur, each costing $O(\log n)$.
- Total: $O(m \log n)$. With $m = n$ iterations, this gives $O(n \log n)$.

## Connections to Bigger Picture

Section 1.2 provides the computational engine that makes the placement evaluation (converting a topological representation into geometric coordinates) efficient enough for use inside combinatorial optimizers like simulated annealing. Without these $O(n \log n)$ data structures, the SA inner loop would be dominated by $O(n^2)$ coordinate computation, severely limiting scalability. The topological representations themselves (sequence-pairs, etc.) are covered in [[1.3 Symmetric-Feasible Sequence-Pairs]], while the overall placement framework incorporating symmetry constraints is detailed in [[1.4 Topological Placement with Symmetry Constraints]]. The choice among these four data structures is largely a practical engineering decision -- they all achieve the same asymptotic bounds, but differ in constant factors, ease of implementation, and behavior when embedded in an annealing loop (the segment tree's one-time construction trick being particularly valuable). Johnson's priority queue reappears later in the chapter when discussing more advanced contour-tracking scenarios.
