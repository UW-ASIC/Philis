# 3.3 B-Tree Placement with Constraints

> **Chapter 3**: Deterministic Analog Placement by Enhanced Shape Functions (Strasser, Eick, Graeb, Schlichtmann)
> **Part**: Part I: Placement

This section covers how **B\*-tree**-based placement representations handle analog-specific constraints -- first for linear constraints (minimum distance, symmetry), then for piecewise-linear constraints (forbidden zones in DTI transistors), and finally introduces **enhanced shape functions** that compactly represent sets of feasible placements.

---

## Key Concepts

### 3.3.1 Linear Constraint Handling

The placement problem uses a **Horizontal Constraint Graph (HCG)** to encode non-overlap and minimum-distance relationships between modules. The optimization target is minimizing the $x$-coordinate of a virtual end node $x_e$, subject to constraints.

- **Partial shadows**: The partial shadow $T_{P,m}$ of a module $m$ cast on the $y$-axis determines which modules interact horizontally. The shadow is defined as:

$$T_{P,m} = [v_m - d_{min}(MR), v_m],$$
$$= [v_B + h_{B_1} \cdot v_m + h_B + d_{min}(m)]$$

  The region of the $y$-axis where modules may be influenced by placement of module $m$ is covered by the partial shadow of $m$.

- **$y$-regions**: To efficiently build the HCG, $y$-regions are defined. All lower and upper $y$-coordinates $v_B$ and $v_B + h_B$ of all modules are sorted in a flat, sorted, unified list. Any zone between two entries of that list is called a **$y$-region**. An **r-tree** data structure stores the sets of modules associated with the $y$-regions, allowing more than one module to be registered with a single region.

- **Algorithm 3.3 -- buildHCG()**: The algorithm constructs the HCG by:
  1. Create start and end HCG nodes.
  2. Create tree of $y$-regions.
  3. Initialize all $y$-regions with the start node.
  4. **For each** module $m$ in its **placement** order:
     - Create a new HCG node for $m$.
     - **For each** region $r$ in the $y$-region range $T_{C,m}$ (core shadow):
       - **For each** module $n$ registered in $r$: if $d_{min}(n, m) < d_{max}(n, m)$, add an edge to the HCG node of $n$ from the HCG node of $m$.
     - Remove all entries in $r$ and register module $m$ in $r$.
     - **For each** region $r$ in $T_{P,m}$ (partial shadow): register module $m$ in $r$.
  5. Remove multiple edges.
  6. Add edges from all nodes in region list to the end node.

- **Core vs. partial shadow**: The **core shadow** $T_{C,m}$ of a module $m$ completely overlaps the lower region. If the core shadow of $a$ overlaps a region, $a$ is registered with all of those regions. A new module $b$ that overlaps these regions receives edges from $a$.

- **Simplex solver**: Using the HCG, the optimization problem is formulated as a minimization of the $x$-coordinate of the virtual end node $x_e$ with respect to all constraints:

$$\mathbf{x}_{opt} = \arg\min_{x_e} x_e$$

subject to:

$$\mathbf{M} \cdot \mathbf{x} \geq \mathbf{d}$$
$$\mathbf{x} \geq \mathbf{0}$$

  plus symmetry and alignment constraints. This is solved by a **Simplex solver**.

### 3.3.2 Piecewise-Linear Constraint Handling

This subsection addresses cases where the allowable distance ranges between modules are **not simply linear**. A key example is **DTI transistors** (see [[3.4 Enhanced Shape Functions|Fig. 3.4]]) where there is a **forbidden zone** between two allowable distance ranges -- meaning the solution space is **concave** (non-convex), and the problem can no longer be formulated as a standard LP.

- **Mixed Integer Programming (MIP)**: The proposed formulation uses a **linear mixed integer programming** solver. A **binary range variable** $r_{e_i}$ is introduced for every edge $e_i$ in the HCG:

$$r_{e_i} \in \{0, 1\}$$

  where $r_{e_i} = 0$ means the weight of edge $e_i$ is in **Range 1** and $r_{e_i} = 1$ means it is in **Range 3** (the two allowable ranges, skipping the forbidden Range 2).

- **Constraint formulation**: For each edge, two inequalities are introduced, together with the range variables. Given $\beta$ as a sufficiently large number:

$$e_i - r_i \cdot \beta \leq s_{max,r1} - s_{min,r1}$$
$$e_i + (1 - r_{e_i}) \cdot \beta \geq d_{r3,min}$$

  These two cases work out as:
  1. **$r_{e_i} = 0$ (Range 1)**: $(3.37)$ reduces to $e_i \leq s_{max,r1} - s_{min,r1}$, and $(3.38)$ reduces to $e_i + \beta \geq d_{r3,min}$ (always fulfilled since $\beta$ is large). Thus $e_i$ cannot exceed its maximum stretching of module $m$ to the right ($s_{max}$).
  2. **$r_{e_i} = 1$ (Range 3)**: $(3.37)$ becomes $e_i - \beta \leq \ldots$ (always satisfied). $(3.38)$ reduces to $e_i \geq d_{r3,min}$, ensuring the distance is at least $d(r3)$.

- **Stretching variables**: To ensure the distance between modules $n$ and $m$ is always sufficient to generate the DTI (as in $(3.39)$), the stretching variables $v_{l,m}$ and $v_{r,m}$ can be calculated from $e_1$ and $e_2$:

$$v_l + v_{l,m} \leq s_{max}$$

  In Range 1 ($r_{e_1} = 0$), the trenches are stretched. The stretching variable $e_2$ must equal $v_{l,m} + s_{l,m}$, made small by a cost function term at $(3.41)$.

- **Solving for $x$-coordinates**: The optimization problem $(3.33)$-$(3.35)$ is extended: for every edge $e_i$ an additional range variable $r_{e_i} \in \{0, 1\}$ and constraints similar to $(3.37)$-$(3.39)$, $(3.41)$, and $(3.42)$ need to be defined. For every module $m$, a constraint similar to $(3.40)$ is added. The cost function $(3.33)$ is extended by a $\lambda$ term, which is made sufficiently small to ensure $x_e$ is the main minimization objective:

$$x_e + \lambda \cdot \sum (v_{l,m} + v_{r,m})$$

  This formulation works with a **linear MIP solver**, with the factor $\lambda$ set to a positive value less than $\frac{w_{min}}{N}$, where $w_{min}$ is the width of the smallest module and $N$ the total number of modules.

## 3.4 Enhanced Shape Functions

### 3.4.1 Review of Shape Functions

A **shape function** (from [38]) is used to calculate compact placements for a set of rectangular modules. Each shape represents a placement with a different **aspect ratio**:
- Formalized as a tuple $(w, h)$ where $w$ and $h$ denote width and height.
- A **recursive algorithm** generates the shape function of a module set: the set is partitioned into two subsets, sub-shape functions are calculated, and all combinations are evaluated.
- **Two types of combination**: horizontal addition (placing side by side) and vertical addition (stacking), where the bounding rectangle is:
  - Horizontal: $(w_1 + w_2, \max(h_1, h_2))$
  - Vertical: $(\max(w_1, w_2), h_1 + h_2)$
- **Suboptimal shapes** (those with a bigger height than others having the same or even a lower width) are removed, as they are dominated. This produces the **Pareto front** of possible placements.
- The continuous shape function can be considered the Pareto front of possible placements -- it represents different placements with different aspect ratios. This is a **second key feature** of shape functions.

### 3.4.2 Definition of Enhanced Shape Functions

Enhanced shape functions extend standard shape functions to handle **non-slicing placements** (placements that cannot be described by a slicing tree). Standard shape functions are limited to slicing tree topologies.

- An enhanced shape is defined as a tuple $(w, h, \alpha)$: the placement's bounding box $(w, h)$ plus its corresponding **B\*-tree** $\alpha$.
- B\*-trees are denoted by Greek lowercase letters. Storing the B\*-tree allows efficient combination of enhanced shape functions and their underlying modules.
- **Suboptimal identification**: An enhanced shape is considered suboptimal in two cases:
  - It has a bigger height than other enhanced shapes having the same or even lower width.
  - It has a higher net-length than other enhanced shapes having the same width and height.

### 3.4.3 Combination of Enhanced Shape Functions

To combine two enhanced shape functions, all of their enhanced shapes are combined **in pairs**. The combination of two enhanced shapes $(w_1, h_1, \alpha)$ and $(w_2, h_2, \beta)$ is calculated using the B\*-trees.

#### Horizontal Addition

For two given B\*-trees $\alpha$ and $\beta$, a **horizontal addition** is performed by attaching the root node of $\beta$ to the lowest, rightmost node of $\alpha$:
- The lowest, rightmost node of a B\*-tree is the node with no right child, where this node itself and all its predecessors are either right children or the root node.
- **Key property**: The resulting placement is compact to the lower left corner. Any constraint satisfied by $\alpha$ and $\beta$ before the addition is also satisfied by the resulting B\*-tree (no additional constraints needed for the supertree).
- The topology of the B\*-trees $\alpha$ and $\beta$ is **not changed** by horizontal addition -- only one edge is added to connect them.
- The in-order and preorder traversals of an arbitrary B\*-tree are defined as ordered lists:

$$\text{in}(\alpha) := \text{in}(b), \alpha, \text{in}(c)$$
$$\text{prec}(\alpha) := \alpha, \text{prec}(b), \text{prec}(c)$$

- Two order relations on the traversals:
  - $a \preceq b$ means "$a$ is a predecessor of $b$ in the inorder traversal."
  - $a \succeq b$ means "$a$ is a predecessor of $b$ in the preorder traversal."
- **Feasibility**: The feasibility of constraints can be checked using the relative positions of the modules in the in- and preorder traversals ([21]). The relative positions of modules in $\alpha$ and $\beta$ in the in- and preorder traversals **do not change** after horizontal addition -- thus, any constraint satisfied before is also satisfied after the addition.

#### Vertical Addition

A **vertical addition** arranges two partial placements vertically. The resulting B\*-tree **cannot** be generated simply by adding an edge from $\alpha$ to $\beta$ (unlike horizontal addition). Instead, a new B\*-tree is iteratively formed:

- The B\*-tree $\beta$ is segmented: the root of each segment being a **baseline module**. All modules reachable from the root node traversing right edges only are placed close to the baseline.
- **Baseline modules** are identified, and **adequate nodes** of $\alpha$ are determined as the new parents of the segment root nodes. This is done using a **contour-based algorithm** that assigns segments "from left to right" in the order given in Fig. 3.28.
- The segments of the B\*-tree $\beta$ are added in ascending order. Before the addition, the in- and preorder positions of the segments fulfill:

$$\text{introot}(\beta_i) \succeq \text{introot}(\beta_{i+1})$$
$$\text{pretroot}(\beta_i) \succeq \text{pretroot}(\beta_{i+1})$$

- The root node of $\beta_i$ is then added to a node of $\alpha$ (denoted $\text{parent}(\beta_i)$) being its **left child**. The segments are added "from left to right," so the parents fulfill:

$$\text{parent}(\beta_i) \preceq \text{parent}(\beta_{i+1})$$

  in both in- and preorder. This ensures the relative positions of modules in $\alpha$, $\beta_i$, and $\beta_{i+1}$ do not change, preserving constraint feasibility.

- **Advantages over standard shape functions**: All suboptimal enhanced shapes are stripped after addition. A **set of possible placements** is stored, instead of a single solution. The addition of two feasible B\*-trees is also a feasible B\*-tree -- an important **closure property**.

## Algorithms & Methods

### Algorithm 3.3: buildHCG()

```
begin
  startNode <- new HCG node as start;
  endNode   <- new HCG node as end;
  create tree of y-regions;
  initialize all y-regions with startNode;
  
  forall modules m in its posnsel do
    mNode <- new HCG node for m;
    forall regions r in T_{C,m} do
      forall modules n registered in r do
        if d_min(n, m) < d_max(n, m) then
          add edge to mNode from HCG node of n;
      remove all entries in r;
      register module m in r;
    forall regions r in T_{P,m} do
      register module m in r;
  
  remove multiple edges;
  add edges from all nodes in region list to endNode;
end
```

**Purpose**: Builds the HCG respecting minimum distance constraints between modules in $O(n \log n)$ time (using the r-tree for region lookups), where $n$ is the number of modules.

### Enhanced Shape Function Combination Pipeline

1. **Partition** the module set recursively into two subsets.
2. **Compute** the enhanced shape function for each subset (recursively).
3. **Combine** the two enhanced shape functions:
   - For each pair of enhanced shapes, perform **horizontal addition** (attach $\beta$ root to lowest-rightmost of $\alpha$).
   - For each pair of enhanced shapes, perform **vertical addition** (segment $\beta$ along baseline modules, attach segments as left children of adequate nodes in $\alpha$).
4. **Prune** suboptimal shapes from the combined set (Pareto filtering on width, height, and net-length).
5. The result is a compact set of **non-dominated placements** with their associated B\*-trees.

### Key Property: Constraint Preservation

Both horizontal and vertical addition preserve the **in-order and preorder traversal** relationships of modules within each original B\*-tree. Since feasibility of analog constraints (symmetry, matching, minimum distance) can be verified from these traversal orderings, any constraint satisfied by the input B\*-trees is **automatically satisfied** by the combined result.

## Connections to Bigger Picture

This section forms the algorithmic core of Chapter 3's deterministic placement approach. The constraint handling methods in Sections 3.3.1-3.3.2 build directly on the **placement constraints** generated in [[3.2 Placement Constraint Generation]], translating analog design rules (symmetry, matching, minimum distance, DTI forbidden zones) into graph-based optimization formulations. The enhanced shape functions of Section 3.4 replace stochastic search (simulated annealing) with a **deterministic enumeration** of compact, feasible placements -- a key differentiator from the approaches in [[2 Placement|Part I's other chapters]]. The B\*-tree representation and its closure properties under addition feed directly into the **hierarchically guided enumeration** described in [[3.5 Hierarchically Guided Enumeration]], which uses the HSMPG tree to manage the combinatorial explosion when applying these operations across an entire circuit hierarchy. The piecewise-linear MIP formulation (Section 3.3.2) is particularly important for modern analog processes where DTI isolation creates non-convex spacing requirements that pure LP-based placers cannot handle.
