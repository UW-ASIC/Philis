# 7.1 Introduction to Constraint-Driven Design

> **Chapter 7**: Constraint-Driven Design Methodology: A Path to Analog Design Automation (Jerke, Lienig, Freuer)
> **Part**: Part III: Layout in the Design Flow

## Key Concepts

### 7.1 Introduction: The Case for Constraint-Driven Design

Physical design automation for analog ICs lags far behind digital design. The root cause is the **analog IC design problem itself**: even small analog circuits carry a rich, interlinked set of constraints that are difficult to formalize.

- Most analog constraints are still specified and considered **manually** by expert designers.
- Constraints are often **implicit** (based on designer experience) rather than **explicit** (formalized), preventing their use in automated flows.
- The **verification gap** is widening: DRC and LVS do not cover all analog constraints (e.g., matching, IR-drop, signal delay).

**Key thesis**: The evolution from polygon pushing (1980s) to schematic-driven layout (1990s) to **constraint-driven design** (2000s+) is a necessary prerequisite for full analog design automation. The ability to "analyze" and "verify" constraints is a precondition for "synthesizing" layouts.

### 7.2 Problem Description

#### 7.2.1 The Design Problem

Any IC design problem is a **constrained optimization problem**:

- The degrees of design freedom span a multidimensional solution space, partially bounded by global design constraints.
- A feasible solution is obtained by **sequentially removing all degrees of design freedom** -- transforming high-freedom functional representations into lower-freedom ones (specification $\to$ netlist $\to$ floorplan $\to$ placement $\to$ routing $\to$ mask layout).
- **Design constraints must be fulfilled**; design objectives *may* be fulfilled. An objective that must be met is, by definition, a constraint.

A critical distinction from digital design: in analog ICs, **multiple design steps are active simultaneously** (e.g., device generation, preplacement, and global routing all happen during floorplanning). This tight coupling is driven by the interdependency of analog constraints.

#### 7.2.2 Analog vs. Digital Design Automation

Despite having fewer devices, analog modules often require **equal or greater design effort** than digital modules. The reasons are:

1. **Richer constraint sets**: Each analog design object (instance, net, path) must satisfy a larger, more diverse set of constraints. Digital designs benefit from higher functional abstraction and fewer top-level constraints.
2. **Unknown constraints**: The majority of analog constraints may be unknown when the design process begins, making automatic top-level planning nearly impossible.
3. **Algorithm scalability**: The conventional one-algorithm-per-constraint-type approach fails for linked (complex) constraints. Each new constraint type potentially requires a new specialized algorithm.
4. **Verification incompleteness**: Digital tools offer consistent, seamless solutions for a small set of constraint types (delay, clock skew). Analog tools lack a **unified constraint description**, leading to inconsistent and non-comprehensive constraint handling.
5. **Overlapping design steps**: Unlike digital design where steps are sequential and separable, analog design steps overlap temporally, requiring simultaneous consideration of multiple constraint types.

### 7.3 Constraint Classification and Representation

Constraints are classified along four axes: **complexity**, **category**, **form**, and **type**.

#### By Complexity

- **Simple constraint**: a relation between *independent* design variables (e.g., $V < 0.1\,\text{V}$).
- **Complex constraint**: a conjunction of simple constraints coupled through *dependent* variables via **design parameter unification**. E.g., the complex constraint $C_c$:

$$\text{starShaped}(N) \;\wedge\; \text{netPin}(N, P_1) \;\wedge\; \text{netPin}(N, P_2) \;\wedge\; \text{irDrop}(P_1, P_2, V) \;\wedge\; V < 0.1\,\text{V}$$

$C_c$ is satisfied iff all four simple constraints are satisfied simultaneously, with the shared design parameters $N$, $P_1$, $P_2$, $V$ unified.

#### By Category

| Category | Purpose | Examples |
|---|---|---|
| **Technology** | Enable manufacturing for a technology node | Wire width, spacing, layer thickness |
| **Functional (electrical)** | Ensure intended IC functionality | Max IR-drop, min gain, max offset voltage |
| **Design methodology (geometry)** | Reduce design complexity, guide transformations | Max hierarchy depth, max devices/cluster, predefined power-routing layer, bus width |
| **Commercial** | Business-driven | Max die area, number of metal layers |

#### By Form

- **Implicit constraints**: Not clearly expressed; may be plain text notes or assumptions built into circuit descriptions. Represent **non-formalized design knowledge**. Example: "differential pair transistors must be placed symmetrically for matching" -- obvious to designers but not easily encoded for automated tools, especially with additional requirements like parasitic interconnect matching. Cannot be used for automated constraint-driven design.
- **Explicit constraints**: Clearly expressed, formalized design knowledge. Accessible to design algorithms. **Primary requirement** for any constraint-driven design flow.

#### By Type

Each constraint has a **type** corresponding to the type of its design variables, with a clearly defined physical/electrical/mechanical/mathematical/geometrical unit (e.g., "IR-drop" $\to$ Volts, "signal delay" $\to$ Seconds). The relevance of a type depends on the specific design context.

#### Uniform Representation via CLP

All constraints and design variables must be represented in a **uniform, abstract form** -- complete and unambiguous -- to enforce common understanding among all design algorithms. **Constraint Logic Programming (CLP)** is the chosen formalism:

- Constraints are defined in the body of **clauses** (conditions).
- Example: The IR-drop constraint $V_{\text{IR}}(P_1, P_2) < 0.1\,\text{V}$ is split into a conjunction:

$$\text{irDrop}(P_1, P_2, V) \;\wedge\; V < 0.1$$

- Structural/contextual constraints (e.g., $\text{netPin}(N, P_1)$, $\text{starShaped}(N)$) are added to embed the constraint within its design context.
- Coupling of simple constraints into complex ones is achieved via **substitution (unification)** of shared design variables.

### 7.4 Components of a Constraint-Driven Design Flow

A constraint-driven design flow requires five complementary components:

1. **Constraint Management** (Sect. 7.4.1)
2. **Constraint Derivation** (Sect. 7.4.2)
3. **Constraint Transformation** (Sect. 7.4.3)
4. **Constraint Sensitivity Analysis** (Sect. 7.4.4)
5. **Constraint Verification** (Sect. 7.4.5)

#### 7.4.1 Constraint Management

Responsible for:

- **Storage** of constraint data and **synchronization** of the link between constraints and design objects.
- Guaranteeing **semantic integrity** across different levels of abstraction.
- Supporting **hierarchical relations** between design objects and dependencies.
- Keeping constraints **consistent and valid** through close interaction with design databases and algorithms.
- Providing **fast access** to constraint information through standardized APIs.

**Over-constraint detection**: When not all constraints can be fulfilled simultaneously, the system faces a **Constraint Satisfaction Problem (CSP)**. Resolution methods include:
- **Constraint propagation**
- **Constraint relaxation**
- **Backtracking**
- **Constraint weights** (common but problematic when many constraints have similar weights)

**Constraint assignment** in a hierarchical design operates in three modes:
- **Top-down**: A single constraint is assigned from a higher level down through the hierarchy (e.g., net shielding from I/O pad down to subcell terminal). One constraint per traversed design object.
- **Bottom-up**: Constraints propagate upward. Allocates as many constraints as instances of that cellview exist in the flattened hierarchy -- **computationally more expensive**.
- **Combined top-down-bottom-up**: Used when constraints must propagate both directions (e.g., I/O pad in a subcell with shielding requirements both above and below).

Assignment can also operate **across the extent of design objects** (e.g., skipping metal resistor instances when propagating net shielding to physically connected nets) and within a **virtual design hierarchy** defined by constraint-linked design objects.

#### 7.4.2 Constraint Derivation

**Constraint derivation** (or generation) translates design objectives into constraints using three methods:

1. **Rule-based derivation**: Fixed rules transform a design objective into a set of constraints, considering the design context. Can be highly automated if the IC specification is in computer-processable form (executable specification).
2. **Deduction-based derivation**: A logic reasoning system draws conclusions from design/constraint data, then applies derivation rules. Enables **abstraction and reuse** -- e.g., if MOS and bipolar transistors are both "transistors", a rule defined for one can be applied to both.
3. **Expert knowledge**: Still required for critical global design objectives that would produce complex constraint sets too difficult for automatic rule-based approaches. Unfortunately, expert knowledge is unstructured and non-formalized.

Constraint transformation (Sect. 7.4.3) is a form of **indirect constraint derivation** since it creates lower-level constraints dependent on higher-level ones.

#### 7.4.3 Constraint Transformation

Translates **higher-level constraints** into equivalent **lower-level constraints** (and vice versa via inverse transformation) using **transformation rules**:

- Simple constraint transformations $\to$ independent equations.
- Complex constraint transformations $\to$ coupled equation systems.
- Multiple transformation rules may apply; the choice **inherently constrains the solution space**, reducing global degrees of design freedom.
- The transformation must be **complete and unambiguous**.
- If lower-level constraints unexpectedly affect higher-level constraints, **design iterations** (backtracking) are required.

**Example**: A maximum IR-drop between an I/O pad and a subcell terminal, given known current flow, may be transformed into:
- Placement constraints (for pad and subcell)
- Routing constraints (wire length, layer, width)

A constraint-driven algorithm can then decide which is more critical (placement vs. routing) and allocate design freedom accordingly.

#### 7.4.4 Constraint Sensitivity Analysis (CSA)

CSA determines the **context-specific sensitivity** of numerical design parameters with respect to related constraints. Two modules:

1. **Sensitivity of design parameters w.r.t. output parameters**: Uses mathematical models (equation systems) of the physical/electrical/geometrical subproblem. Methods include:
   - Local methods (partial derivatives)
   - Statistical methods (sampling, Bayesian, Monte Carlo)

2. **Relative distance of a parameter value to its constraint boundaries**: For constraints $x_l \le x \le x_u$:

$$d_l(x) = \exp(x_l - x) - 1 \qquad d_u(x) = \exp(x - x_u) - 1$$

- $d_l = 0$: parameter matches lower bound exactly
- $d_l > 0$: constraint violation
- $d_l < 0$: no violation (and analogously for $d_u$)

**Applications of CSA**:

- **Guiding design decisions**: Focus on high-sensitivity parameters for important output parameters, or on low-sensitivity ones, depending on strategy.
- **Prioritizing constraint violations**: Parameters violating constraints get higher priority.
- **Identifying design task parallelism**: Weakly coupled parameter groups (low mutual sensitivity) can be partitioned and solved independently in parallel.

**IR-drop wire routing example** (Fig. 7.6): Given a wire near a heat source with $V_{\text{IR}} \le V_{\text{IR,max}}$ and $V_{\text{IR}} = i \cdot \frac{\rho \cdot l}{w \cdot d} \cdot (1 + \text{TK}_1 \cdot (T - T_{\text{ref}}))$:
- For $w \le w_1$: wire width $w$ has **high sensitivity** to $V_{\text{IR}}$ -- modifying $w$ is the primary choice.
- For $w > w_1$: $w$ loses its impact; temperature $T$ (wire location) becomes the dominant parameter.
- CSA acts as a **filter** to identify which parameters need consideration in a given context.

#### 7.4.5 Constraint Verification

Two verification tasks:

1. **Compliance verification**: Does a design result satisfy all given constraints?
2. **Conflict detection**: Does the constraint set contain mutual conflicts (over-constraints)?

**The verification gap**: Conventional DRC/LVS does not cover all analog constraints. Commercial tools with limited constraint verification: Mentor Graphics Calibre PERC, Cadence Virtuoso IC 6.1.

**The meta-verification approach**: Complex verification problems are **decomposed into smaller, independent subproblems** solvable by existing verification algorithms. The framework:
- References external tool functionality (design data access, specialized verification functions).
- Creates an abstraction layer around multiple design/verification tools.
- Manages correct execution of meta-verification tasks.
- Handles both independent and coupled (dependent) verification problems.
- Detects over-constraints via logical conclusions from constraint and design data.

**Verification rule development**:
1. Define and formalize the constraint verification task.
2. Translate into constraint verification rules.
3. Apply rules (context-dependent) for verification.

**Optimization**: Within CLP-based meta-verification rules, shift long-running sub-verification tasks to the end. Earlier sub-tasks that fail prevent unnecessary execution of later, potentially expensive tasks.

**Static vs. Dynamic constraint verification**:
- **Static**: Constraint and design data are constant (e.g., sign-off verification). Lower overhead -- databases accessed once during initialization.
- **Dynamic**: Data changes during analysis or design steps (e.g., "what-if" analyses by design algorithms). Higher overhead due to cumulative data latency from frequent data access.

Both can be applied to the full constraint/design dataset or a context-specific subset.

### 7.5 Constraint Engineering (Preview)

**Constraint engineering** = the application and handling of constraints during the IC design process. The **Constraint Engineering System (CES)** is a framework combining:

- A **CLP Core** for formal constraint representation and logic reasoning
- **Constraint solvers** (extended linear arithmetic, CHR, other domain-specific solvers)
- **CSA** module
- **Core extensions** for additional functionality
- **Technology abstraction** layer supporting multiple technology nodes
- **Tool Integration Kits (TIK)** that transform tool-specific data into CLP language and vice versa, connecting to: requirement management, schematic editor, layout editor, constraint management, DRC/LVS, and other tools

#### Constraint Programming via CLP

- CLP is chosen for its **stateless, declarative** nature -- you formalize the *problem*, not the *solution*.
- Reduces effort for providing rules for derivation, transformation, and verification compared to imperative approaches.

#### Constraint Handling Rules (CHR)

Introduced in 1991, CHR enables easy definition of new constraint solvers through:
- **Propagation rules**: Derive new constraints from existing ones. E.g., from $A \le B$ and $B \le C$, derive $A \le C$.
- **Simplification rules**: Remove redundant constraints. E.g., from $A \le 5$ and $A \le 7$, remove $A \le 7$.
- **Simpagation**: Combines both simplification and propagation in a single rule (for efficiency).

## Algorithms & Methods

### Meta-Verification Algorithm

The meta-verification approach for complex constraint verification:

1. **Define** the complex verification task formally.
2. **Decompose** into a set of simpler, usually independent sub-verification problems.
3. **Map** each sub-problem to an existing verification algorithm (possibly from external tools via TIK).
4. **Order** sub-verification tasks: place short-running tasks first, long-running tasks last.
5. **Execute** sequentially: if any sub-task reveals a violation, skip all subsequent (potentially expensive) sub-tasks.
6. **Aggregate** results: the complex constraint is satisfied iff all sub-verification tasks pass.

For coupled verification problems, the CLP-based approach draws logical conclusions from constraint and design data to detect mutual conflicts (over-constraints).

### Constraint Satisfaction Resolution

When over-constraints are detected, resolution proceeds via:

1. **Constraint propagation**: Derive implied constraints to reduce the search space.
2. **Constraint relaxation**: Relax less critical constraints (using weights, though this degrades with many similarly-weighted constraints).
3. **Backtracking**: Undo design decisions and try alternatives.
4. **CHR rules**: Apply propagation/simplification/simpagation rules to simplify the constraint set.

### Constraint Sensitivity Analysis Algorithm

1. Build a mathematical model of the design subproblem (equation system with design and output parameters).
2. Compute sensitivity using local (partial derivative) or statistical (Monte Carlo, Bayesian) methods.
3. Compute relative distances $d_l(x)$ and $d_u(x)$ for each parameter $x$ w.r.t. its constraint bounds.
4. Identify high-sensitivity parameters and constraint-violating parameters.
5. Partition weakly coupled parameter groups for parallel design task execution.
6. Feed sensitivity information into design algorithms for context-aware decision-making.
