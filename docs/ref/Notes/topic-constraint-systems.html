Constraint architecture and consistency

Type requirements, trace their origin, preserve them through hierarchy, and diagnose conflicts.

A constraint system is the executable record of design intent

The engine needs to know not only what a rule checks but why the rule exists, which objects it applies to, how it was derived, and what would invalidate that derivation. A flat list of penalty functions cannot answer those questions. A constraint system should connect high-level electrical specifications to physical choices and verification evidence while preserving the distinction between mandatory requirements, limited budgets and optional preferences.

The constraint-engineering chapter of Analog Layout Synthesis treats generation, transformation, management and verification as separate activities. This is a useful architectural foundation: recognize an electrical relationship, express its intent, choose a valid physical implementation, and verify the result. Conflating these stages can make one convenient implementation, such as geometric symmetry, appear to be the original electrical specification. Topological Approaches, PDF pp. 281–291.

Proposed engine principle: every imposed action should carry a short causal explanation. “These devices move together because they share a required symmetry axis” is different from “these devices are pulled together because a calibrated spatial mismatch model predicts lower offset variance.” The former is an exact relation once selected; the latter is a model-based improvement with tradeoffs and a domain of validity.

Give each requirement a complete semantic record

A useful record contains a stable identity; semantic kind; target objects; physical units; predicate or objective; enforcement mode; numerical tolerance; applicable scenarios; provenance; parent requirements; model revision; and evidence status. A separate expression captures alternative implementations or disjunctions. Keep these fields explicit because their meanings affect optimization and reporting, not merely logging.

Philis already has an important separation in Requirements<On> (line 18): hard, budget and cost collections. Rule (line 9) exposes satisfaction, residual, usage, applicability, projection, touched objects and retargeting. Preserve that useful evaluation interface while adding stable semantic records around it. The hot scoring path need not parse a large provenance graph on every move; compiled evaluators can reference immutable records by ID.

Default objective-only rules should remain clearly objective-only. If a rule's default satisfaction predicate always returns true, registering it as a hard requirement without a real predicate does not make the physics checked. Add a construction-time capability check: each enforcement mode requires the evaluator methods needed to support its claim.

Preserve the chain from specification to physical action

Suppose a sensitive supply branch allows at most 2 mV of DC drop and carries a verified 100 µA worst-case current. The parent electrical condition implies total branch resistance no greater than 20 Ω. If a chosen via structure consumes 4 Ω, the wire has 16 Ω left. On a layer with R□ = 0.08 Ω/square and a selected width of 0.4 µm, a uniform-wire approximation gives L ≤ 16 × 0.4 / 0.08 = 80 µm. This is an invented worked example, but every derivation step is dimensionally explicit.

If the router changes width, layer, via count or branch topology, the 80 µm child constraint becomes stale. The voltage-drop requirement still stands. Recompute the child or evaluate the parent directly. If branch current changes after resizing, invalidate the entire dependent chain. This is the practical reason to retain parent-child links rather than copying 80 into a field named “maximum length.”

The generic ParasiticBudget::extract helper documents placeholder length budgets, but the active annotator routing path constructs per-net limits from class/load-derived capacitance allowances divided by the process wire capacitance per unit length. Preserve that existing derivation and expose its provenance and assumptions. Extend it with circuit-performance sensitivities where supported; otherwise retain its heuristic status. A geometric shortcut and an electrical certificate can coexist, but their evidence levels must remain distinct.

Generate intent first; choose the implementation afterward

Pattern recognition can identify a differential pair, current mirror or stack. That is evidence of a functional relationship, not proof that every member must use one particular physical pattern. A differential pair may need matching, equivalent electrical environment and suitable isolation; an ABBA arrangement, a two-dimensional common centroid or another validated template may implement those needs with different routing costs. Retain alternatives until the implementation choice is justified by process, ratios, geometry and electrical priorities. Topological Approaches, PDF pp. 288–291.

The annotator's placement (line 53) already translates recognized blocks into matching, proximity, thermal, centroid, symmetry and DTI rules. Extend each emitted requirement with its origin: recognition rule, circuit members, confidence or checked preconditions, and a numerical parameter source. For example, the thermal difference and proximity constants near lines 37–43 are tuning defaults rather than PDK-derived physical limits. Preserving that distinction makes later calibration possible.

Constraint transformation needs a stated logical relationship. A conservative child rule should imply its parent within declared assumptions; a heuristic proxy merely correlates with parent improvement; an exact reformulation is equivalent. These are not interchangeable. An independently allocated capacitance box may imply a coupled performance bound but exclude feasible candidates outside the box. That is a deliberate conservative transformation that can be relaxed or reallocated while preserving the parent.

Meta-rules can combine measured quantities, layout geometry and simulator results. The source discusses this broader verification model because DRC and LVS alone do not establish all analog intent. Implement meta-rules with explicit dependencies and deterministic evaluation order; a rule depending on extraction cannot be marked passed using a placement-only snapshot. PDF pp. 291–298.

Keep identities and weights through merging, splitting and hierarchy

Physical transformations are often many-to-many. One schematic device can become several fingers; several devices can share a macro; a shield requirement can apply across several connected shapes; a matched array may span hierarchy boundaries. A one-to-one device-index remap is insufficient to preserve every semantic relation. Maintain a realization map from electrical entities to weighted physical units and terminals.

Consider an electrical common centroid with weights wi. Its x condition is ΣA wi xi / ΣA wi = ΣB wi xi / ΣB wi, with a corresponding y condition. The weights should represent the intended matched quantity, commonly equal unit counts or calibrated electrical contribution. A macro's bounding-box area can change when a halo or pin-access region changes while its electrical contribution remains identical. Replacing wi by that area then changes the meaning of the constraint.

Philis's CentroidGroup::centroid (line 32) uses drawn bounding-box area, and its retargeting repeats IDs when members share a cell. Treat that as a geometric approximation unless the generator guarantees proportionality to intended electrical weights. A stronger interface preserves unit weights and first moments through collapse. Verify that changing a non-electrical halo does not change the target electrical centroid.

Stable IDs also matter to optimizer state. The current order contract at lines 15–17 states that prices are matched by kind and ordinal among that kind; reordering silently moves prices. Prices::bind (line 70) and keys implement this mapping. Assign persistent semantic IDs and explicit model revisions so insertion of a new thermal pair cannot transfer another pair's learned price. Carry branch identity by the same principle.

Distinguish inconsistent intent from a failed search

Take a mirror pair with xA + xB = 2a. Suppose fixed placements require xA = 10 and xB = 170, while a fixed axis requires a = 100. The first two imply a = 90; all three together are inconsistent. Moving the axis would resolve the conflict only if the axis is genuinely free. A solver should return the conflicting assumptions, not endlessly increase a symmetry penalty or move a fixed block silently.

Check easy contradictions before expensive search: impossible fixed equalities, empty variant domains, inconsistent ratio requirements, impossible die bounds, incompatible orientations and units. Check integer-grid compatibility explicitly. Mirror and centroid equations can require half-grid coordinates; a doubled-coordinate representation can express them exactly where the permitted physical grid allows it. Rounding each partner independently can turn a solvable continuous relation into an unacknowledged mismatch.

For a linear or finite constraint subproblem, obtain an infeasible core or solver certificate when available. For a heuristic placer, distinguish “no solution found within this runtime and representation” from proven infeasibility. If a restricted hierarchy fails, widening the representation is different from relaxing the electrical requirement. The source's constraint-management discussion treats overconstraint and gradual removal of degrees of freedom as central design issues. PDF pp. 299–302.

Use four outcomes: passed, failed, unknown and not applicable

A thermal constraint with missing dissipation data is unknown unless a separate model proves the absence of relevant heating. A thermal constraint on a domain intentionally outside the thermal analysis scope may be not applicable for that stage. A routing capacitance check on an unconnected net is not evidence of complete electrical success even if its zero drawn length satisfies a cap. These distinctions prevent missing work from improving the score.

The Rule::applicable interface (line 51) documents vacuous satisfaction for inapplicable rules. Preserve a separate completeness layer that distinguishes genuine inapplicability from absent model inputs. Each mandatory requirement needs an accepted outcome before final completion. Optimizers may temporarily use estimates, but final reporting should show which obligations remain unresolved.

Verification evidence should identify candidate geometry hash, electrical mapping, PDK/rule-deck revision, extraction or simulation settings, scenario, evaluator version, numerical tolerance and outcome. A later reshape invalidates geometric and parasitic evidence touching that shape. A bias change invalidates current-dependent reliability evidence even if geometry is unchanged. Dependency-driven invalidation makes those effects explicit and avoids rerunning unrelated checks.

Use cheap checks first when they can safely reject a candidate. Geometry legality and connectivity may eliminate a candidate before expensive circuit simulation. However, a cheap check cannot certify a stronger property than its model supports. The source's static versus dynamic checking distinction supports an incremental evaluator with snapshots rather than an undifferentiated final checklist. PDF pp. 291–298.

Implementation sequence justified by failure prevention

  1. Add immutable IDs, units and provenance around existing rule batches. This fixes price and diagnostic identity without replacing working evaluators.
  2. Represent generated, transformed and verified versions separately. A derived length cap can then be invalidated while the parent voltage-drop obligation survives.
  3. Preserve realization maps through cell generation and hierarchy. This prevents merged devices, finger multiplicities and terminal changes from corrupting matching semantics.
  4. Add pre-search consistency checks and explicit unknown outcomes. Early contradictions become actionable explanations instead of wasted search; missing analysis no longer appears as success.
  5. Attach candidate-specific certificates and dependency invalidation. This makes reported evidence correspond to the layout actually delivered.

Verify identity preservation by reordering and inserting same-kind constraints while confirming prices and diagnostics stay attached to their original semantic targets. Verify transformation soundness on tiny analytic electrical examples. Verify conflict explanations with the three-equation mirror example and a grid-incompatible variant. Verify evidence invalidation by changing only width, current or PDK revision and checking exactly the affected records. These tests exercise the promised semantics rather than mirroring individual methods.

A complete constraint system does not mean inventing every conceivable rule. It means that every requirement actually in the design contract has a defined meaning, an implementation path, and evidence tied to the delivered state. That is the infrastructure needed to justify an “optimal layout” claim at any stated level of model fidelity.
